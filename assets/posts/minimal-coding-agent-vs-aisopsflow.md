# 최소주의 코딩 에이전트와 AISOpsFlow를 비교해보며

Mario Zechner의 글 [What I learned building an opinionated and minimal coding agent](https://mariozechner.at/posts/2025-11-30-pi-coding-agent/)를 읽고 나서 AISOpsFlow를 다시 바라보게 됐다.

두 프로젝트는 겉으로 보면 꽤 다르다. 하나는 개발자가 터미널에서 코드를 작성하도록 돕는 coding agent이고, 다른 하나는 알림을 받아 승인과 실행, 보고까지 연결하는 Ops/IT 자동화 플랫폼이다. 하지만 둘 다 결국 같은 질문을 다룬다.

> 모델이나 기능을 더 많이 붙이는 것보다, 에이전트가 무엇을 보고 무엇을 실행하며 그 결과를 어떻게 남기는지를 얼마나 명확하게 설계할 것인가?

이 글은 pi-coding-agent와 AISOpsFlow를 같은 제품이라고 주장하려는 비교가 아니다. 오히려 pi의 설계 철학을 AISOpsFlow의 관점에 대입해보면서, 개인 개발 도구의 최소주의가 운영 자동화 제품에서는 어디까지 유효하고 어디서부터 다른 원칙이 필요한지 정리한 기록이다.

## 먼저, 두 제품은 무엇을 자동화하는가

pi-coding-agent는 개발자의 작업 세션을 자동화한다. 파일을 읽고, 명령을 실행하고, 코드를 수정하고, 그 과정을 다시 모델의 컨텍스트로 넣는다. 글에서 소개하는 핵심 구성은 다음 네 가지다.

- `pi-ai`: 여러 LLM provider를 하나의 API로 다루는 계층
- `pi-agent-core`: 도구 실행과 이벤트 스트리밍을 담당하는 agent loop
- `pi-tui`: 터미널에서 세션을 관찰하고 조작하는 UI
- `pi-coding-agent`: 세션, 프로젝트 컨텍스트, 커스텀 도구를 연결한 CLI

반면 AISOpsFlow의 중심 흐름은 `alerts → approval → actions → reporting`이다. 개발자의 한 번의 코딩 세션이 아니라, 운영 이벤트가 조직의 절차를 통과하고 실제 환경에서 실행된 뒤 결과와 이력이 남는 흐름을 다룬다.

AISOpsFlow는 이 흐름을 `Core`, `Runner`, `Plugin`으로 나눈다. Core는 정책과 제어를 담당하고, Runner는 고객사 환경 안에서 실제 실행을 담당한다. 클라우드 Core와 온프레미스 Runner는 gRPC streaming과 mTLS로 연결하며, Slack·Email·Telegram·Kakao 같은 채널과 도구는 HTTP/JSON 계약을 통해 Plugin으로 확장한다.

따라서 가장 짧은 정의는 이렇다.

- pi는 **개발자 한 명의 작업 컨텍스트를 실행하는 harness**다.
- AISOpsFlow는 **조직의 운영 절차와 실행 경계를 관리하는 harness**다.

## 공통점은 기능 목록보다 경계에 있다

두 제품을 기능 개수로 비교하면 공통점이 잘 보이지 않는다. pi에는 파일 읽기와 bash가 있고 AISOpsFlow에는 알림, 승인, 플러그인과 Runner가 있다. 하지만 구조적으로 보면 다음 네 가지 원칙이 겹친다.

### 1. 컨텍스트를 통제해야 실행 품질이 올라간다

Mario는 기존 coding harness가 모델의 컨텍스트에 무엇을 몰래 주입하는지 충분히 보여주지 않는 문제를 지적한다. 그래서 pi는 컨텍스트와 세션 형식을 단순하고 관찰 가능하게 만들고, 프로젝트의 `AGENTS.md`를 명시적인 확장 지점으로 둔다.

AISOpsFlow에서 같은 문제는 다른 형태로 나타난다. 모델에게 어떤 문서를 보여줄 것인가보다, 어떤 운영 이벤트가 어떤 정책과 승인 상태를 거쳐 실행 가능한 상태가 되는지가 중요하다. 운영 컨텍스트에는 최소한 다음 정보가 필요하다.

- 어떤 시스템에서 어떤 이벤트가 발생했는가
- 이 이벤트가 어떤 정책과 워크플로우에 매칭됐는가
- 누가 승인했으며 어떤 입력이 변경됐는가
- 어느 Runner와 Plugin이 어떤 권한으로 실행하는가
- 결과와 실패 원인이 무엇인가

pi가 모델 컨텍스트의 투명성을 강조한다면, AISOpsFlow는 운영 컨텍스트의 투명성을 제품의 핵심으로 삼아야 한다. 둘 다 “에이전트가 알아서 판단했다”는 설명으로는 충분하지 않다는 결론에 도달한다.

### 2. 작은 원시 기능이 조합을 만든다

pi는 시스템 프롬프트와 기본 도구를 극도로 줄였다. 기본 도구는 `read`, `write`, `edit`, `bash` 네 가지이며, 저자는 이 정도면 효과적인 coding agent를 만들 수 있다고 본다. 기능을 추가하는 대신 모델이 이미 알고 있는 일반적인 도구 사용 능력을 믿는 방식이다.

AISOpsFlow의 Plugin도 같은 방향으로 볼 수 있다. 모든 채널과 외부 시스템을 Core에 직접 넣는 대신, 계약을 지키는 Plugin으로 분리하면 Core는 흐름과 정책에 집중할 수 있다. 새로운 알림 채널이나 운영 도구를 추가할 때 플랫폼 전체를 다시 설계하지 않아도 된다.

다만 운영 환경의 “작은 원시 기능”은 단순히 API 호출만을 뜻하지 않는다. 실행 결과, 재시도, 타임아웃, 중복 실행 방지, 권한, 감사 이력까지 계약에 포함되어야 실제로 조합 가능한 운영 단위가 된다. 개발자 개인의 bash가 충분한 경우와 조직의 운영 자동화에 bash만으로는 부족한 경우를 구분해야 한다.

### 3. 관찰 가능성은 부가 기능이 아니다

pi의 중요한 선택 중 하나는 세션을 사람이 읽고, 저장하고, 다시 이어갈 수 있게 하는 것이다. 계획을 별도 파일로 쓰고, 도구 호출과 결과를 세션 안에서 확인하고, 필요하면 다른 UI나 후처리 도구를 만들 수 있도록 한다.

AISOpsFlow의 reporting은 이 운영 버전이다. 운영팀이 필요한 것은 “성공했습니다”라는 최종 문장만이 아니다. 어떤 알림이 들어왔고, 어떤 승인과 정책 평가가 있었고, 어떤 Plugin이 어느 Runner에서 실행됐으며, 중간에 어떤 오류가 났는지를 확인할 수 있어야 한다.

이 관점에서 reporting은 실행이 끝난 뒤 만드는 리포트가 아니라, 실행 과정에서 수집되는 이벤트 모델의 결과여야 한다. Core와 Runner를 분리했다면 두 영역의 이벤트를 하나의 실행 추적 단위로 연결하는 것이 중요하다.

### 4. 확장보다 예측 가능성이 먼저다

pi는 MCP, built-in plan mode, background bash, dedicated sub-agent를 넣지 않기로 했다. 이것은 기능을 만들 수 없어서가 아니라, 컨텍스트 오염과 복잡한 상태, 낮은 가시성을 감수하면서까지 기본 기능으로 넣을 필요가 없다고 판단했기 때문이다.

AISOpsFlow도 같은 질문을 던질 필요가 있다.

> 이 기능이 정말 운영 절차를 단순하게 만드는가, 아니면 플랫폼이 관리해야 할 숨은 상태를 늘리는가?

운영 플랫폼에서는 기능을 무조건 제거할 수 없다. 승인과 감사, 정책, 재시도는 오히려 반드시 필요할 수 있다. 대신 각각을 Core의 명시적인 상태와 이벤트로 만들고, 실행 주체와 책임 범위를 분명히 해야 한다. “최소 기능”이 아니라 “최소한의 숨은 상태”가 더 정확한 목표다.

## 한눈에 보는 차이

| 비교 축 | pi-coding-agent | AISOpsFlow |
| --- | --- | --- |
| 주 사용자 | 개발자 | 운영팀, IT 관리자, 조직의 승인자 |
| 기본 단위 | coding session과 agent turn | workflow run과 운영 이벤트 |
| 작업 대상 | 파일, 코드, 로컬 명령 | 알림, 승인, 외부 시스템과 운영 작업 |
| 실행 위치 | 개발자의 로컬 환경 | Core가 제어하고 Runner가 고객 환경에서 실행 |
| 확장 방식 | 커스텀 도구, CLI, 프로젝트 컨텍스트 | Plugin SDK와 Plugin Catalog, HTTP/JSON 계약 |
| 기본 철학 | 낮은 추상화, 높은 직접성 | 정책화된 실행, 분리된 보안 경계 |
| 관찰 대상 | 모델 대화, 도구 호출, 세션 파일 | 이벤트, 승인, 실행 결과, 감사와 보고 |
| 실패의 의미 | 작업을 다시 지시하거나 세션을 수정 | 재시도·중단·승인 재요청·사고 대응으로 연결 |

이 표에서 가장 중요한 차이는 실패의 반경이다. pi에서 잘못된 명령은 대체로 현재 개발 작업을 망가뜨린다. AISOpsFlow에서 잘못된 실행은 서비스 장애, 데이터 변경, 보안 사고로 이어질 수 있다. 같은 “도구 호출”이라도 운영 플랫폼에서는 실행 전후의 통제면이 훨씬 넓어져야 하는 이유다.

## pi의 선택을 AISOpsFlow에 번역한다면

pi의 설계를 그대로 복사할 수는 없지만, 다음과 같이 번역하면 유용하다.

| pi의 개념 | AISOpsFlow에서의 대응 | 설계 질문 |
| --- | --- | --- |
| session | workflow run | 실행을 어디까지 재개·분기·재생할 것인가? |
| `AGENTS.md` | workflow context와 정책 | 실행에 필요한 정보와 정책을 어떻게 명시할 것인가? |
| `read/write/edit/bash` | Plugin action | 입력·출력·권한·실패를 어떤 계약으로 고정할 것인가? |
| agent event stream | Core–Runner event stream | 실행 중 상태를 누가 언제 볼 수 있는가? |
| terminal scrollback | reporting/audit timeline | 사람이 나중에 같은 실행을 재구성할 수 있는가? |
| YOLO mode | 승인된 실행 모드 | 자동 실행과 사람 승인의 경계를 어디에 둘 것인가? |

특히 `session`과 `workflow run`을 대응시키는 시각이 중요하다. 둘 다 한 번의 입력과 여러 도구 실행, 중간 결과, 최종 상태를 묶는다. 하지만 workflow run은 여러 사람이 관여하고, 실행 환경이 원격이며, 재시도와 권한의 의미가 있기 때문에 더 강한 상태 모델이 필요하다.

pi가 세션을 JSON으로 저장하고 다른 모델이나 UI에서 이어갈 수 있도록 한 것처럼, AISOpsFlow도 실행 이력을 특정 화면에만 가두지 않는 편이 좋다. 실행 이벤트를 명확한 스키마로 남겨야 콘솔, 알림, 리포트, 감사 시스템이 같은 사실을 바라볼 수 있다.

## 가장 큰 차이: YOLO는 철학이지만 운영에서는 정책이 된다

pi는 기본적으로 YOLO다. 파일과 명령에 제한 없이 접근하고, 사용자가 그 위험을 이해한 상태에서 생산성을 얻는 것을 선택한다. 글의 논지는 꽤 현실적이다. 에이전트가 파일을 읽고 코드를 실행하고 네트워크까지 사용할 수 있다면, 얕은 승인 프롬프트만으로 안전을 보장한다고 말하기 어렵다. 정말 중요한 격리는 컨테이너나 실행 환경의 경계에서 만들어야 한다.

AISOpsFlow는 여기서 다른 결론을 내릴 수밖에 없다. 운영 자동화에서 사용자에게 모든 책임을 넘기는 것은 제품의 목적과 맞지 않는다. 그렇다고 모든 실행을 수동 승인으로 막으면 자동화의 가치가 사라진다. 그래서 Core와 Runner를 분리하는 구조가 의미를 갖는다.

- Core에서는 정책, 승인, 대상, 실행 계획을 판단한다.
- Runner에서는 고객 환경 내부의 실제 권한과 연결을 사용한다.
- Plugin은 허용된 계약 안에서 외부 채널과 도구를 호출한다.
- 결과는 다시 Core의 실행 상태와 보고 체계로 돌아온다.

즉, AISOpsFlow의 목표는 “YOLO를 없애는 것”이 아니라 **YOLO가 허용되는 범위를 시스템적으로 좁히고, 그 범위 안의 실행을 추적 가능하게 만드는 것**에 가깝다. 개인 개발 환경에서는 사용자의 판단이 경계가 될 수 있지만, 기업 운영에서는 정책과 실행 경계를 제품이 제공해야 한다.

## 계획과 서브에이전트에 대한 서로 다른 답

pi는 built-in TODO와 plan mode를 제공하지 않는다. 필요한 계획은 `TODO.md`나 `PLAN.md` 같은 파일로 관리한다. 계획이 파일에 남으면 세션 사이에 공유되고 버전 관리도 가능하며, 모델이 무엇을 읽었는지 사람이 직접 확인할 수 있다는 장점이 있다.

AISOpsFlow의 workflow는 이 아이디어와 닮았지만, 더 강한 의미를 가진다. 운영 워크플로우는 단순한 모델의 메모가 아니라 실제 실행을 제한하는 계약이어야 한다. 단계, 조건, 승인, 실패 분기, 출력 형식이 실행 상태로 남아야 한다.

여기서 pi의 “서브에이전트를 많이 만들지 말라”는 조언도 참고할 만하다. 컨텍스트를 나누기 위해 무작정 여러 에이전트를 병렬 실행하면 책임과 결과를 추적하기 어려워진다. AISOpsFlow에서도 병렬화는 멋진 기능이 아니라 운영상 필요한 경우에만 선택해야 한다. 병렬 실행을 도입한다면 각 실행의 책임, 상관관계 ID, 실패 처리, 합류 조건을 먼저 정의해야 한다.

## 결론: AISOpsFlow는 운영을 위한 agent harness다

pi-coding-agent에서 가장 인상적인 점은 “기능이 적다”는 사실 자체가 아니다. 무엇을 만들지보다 무엇을 만들지 않을지를 명확히 결정하고, 그 선택을 컨텍스트·도구·UI·세션 모델 전체에 일관되게 반영했다는 점이다.

AISOpsFlow에도 같은 종류의 일관성이 필요하다. 다만 AISOpsFlow가 최소화해야 할 것은 기능 수가 아니라 운영자의 불확실성이다.

- 어떤 이벤트가 실행을 시작했는가
- 어떤 정책과 승인이 실행을 허용했는가
- 실제로 어느 Runner와 Plugin이 동작했는가
- 실패했을 때 무엇이 자동으로 복구되고 무엇이 사람에게 넘어가는가
- 시간이 지난 뒤 같은 실행을 다시 설명할 수 있는가

이 질문에 답할 수 있다면 AISOpsFlow는 단순한 알림 연동 도구를 넘어선다. Core는 운영의 판단과 통제를 맡고, Runner는 실행 경계를 맡고, Plugin은 확장 가능한 손발이 된다. 이 구조는 pi가 개발자의 세션을 단순하게 유지하기 위해 선택한 harness 설계와 같은 방향을 바라보지만, 적용 대상이 조직 운영인 만큼 승인·정책·감사라는 층을 추가로 요구한다.

그래서 두 제품의 관계를 한 문장으로 정리하면 다음과 같다.

> pi는 “개발자가 에이전트를 믿고 함께 일하려면 무엇을 투명하게 만들어야 하는가”를 묻고, AISOpsFlow는 “조직이 자동화된 실행을 믿으려면 무엇을 통제하고 기록해야 하는가”를 묻는다.

좋은 운영 자동화는 거대한 기능 목록에서 시작하지 않는다. 명확한 컨텍스트, 작은 실행 단위, 안정적인 계약, 그리고 끝까지 남는 관찰 가능성에서 시작한다.
