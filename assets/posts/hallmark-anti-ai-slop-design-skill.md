# Hallmark: AI가 만든 듯한 웹을 피하는 디자인 스킬

생성형 AI로 웹 화면을 만드는 일은 놀라울 정도로 빨라졌다. 짧은 설명만으로 랜딩 페이지와 대시보드의 뼈대를 만들고, 컴포넌트와 스타일을 연결하고, 반응형 화면까지 한 번에 얻을 수 있다.

그런데 속도가 빨라질수록 비슷한 화면도 많아졌다. 둥근 카드, 무난한 산세리프 폰트, 보라색 그라데이션, 넓은 히어로 영역, 익숙한 버튼과 배지. 기능은 다르지만 첫인상은 비슷한 웹사이트가 계속 만들어진다.

Nutlope의 `hallmark`는 이 문제를 정면으로 다루는 디자인 스킬이다. Claude Code, Cursor, Codex 같은 코딩 에이전트가 웹 UI를 만들 때 흔히 선택하는 안전한 기본값을 경계하고, 각 프로젝트의 목적에 맞는 구조와 시각적 방향을 선택하도록 유도한다.

핵심 질문은 단순하다.

> AI에게 화면을 만들어달라고 할 때, 어떻게 하면 결과물이 “AI가 만든 화면”이 아니라 하나의 브랜드와 제품처럼 보이게 할 수 있을까?

## Hallmark는 UI 컴포넌트 모음이 아니다

Hallmark를 새로운 CSS 프레임워크나 디자인 시스템으로 이해하면 핵심을 놓치게 된다. 이 프로젝트는 특정 버튼, 카드, 내비게이션을 제공하는 대신 에이전트가 디자인을 결정하는 방법에 개입한다.

일반적인 UI 생성 흐름은 대체로 다음과 같다.

1. 사용자의 요구사항에서 페이지 유형을 추정한다.
2. 익숙한 레이아웃과 컴포넌트를 조합한다.
3. 무난한 색상과 폰트를 적용한다.
4. 코드가 실행되는지 확인한다.

Hallmark는 여기에 다른 질문을 추가한다.

- 이 브랜드에 어울리는 구조인가?
- 페이지의 시각적 중심이 분명한가?
- 업종과 목적에 맞는 밀도와 리듬을 갖고 있는가?
- 다른 AI 생성 페이지와 구별되는 흔적이 있는가?
- 구현하기 쉬운 기본값을 선택했다는 이유만으로 디자인을 결정하지 않았는가?

즉 Hallmark는 “화면을 만들라”는 요청을 “명확한 디자인 방향을 가진 화면을 만들고, 결과를 스스로 비평하라”는 작업으로 바꾼다.

## 네 가지 동사로 이해하는 Hallmark

Hallmark의 사용 방식은 네 가지 동사로 정리된다.

| 명령 | 역할 |
| --- | --- |
| 기본 실행 | 새 UI를 만든다. 요구사항에 맞는 구조와 테마를 고르고 안티패턴을 검사한다. |
| `hallmark audit <target>` | 기존 코드의 디자인 문제를 점검하고 수정 목록을 제시한다. |
| `hallmark redesign <target>` | 카피와 정보 구조, 브랜드 방향은 유지하면서 시각 구조를 다시 만든다. |
| `hallmark study <screenshot \| URL>` | 참고 디자인의 구조와 타이포그래피, 색상 관계를 분석한다. |

이 구성이 좋은 이유는 디자인 작업을 “새로 만들기” 하나로 한정하지 않기 때문이다. 이미 있는 화면을 평가할 수도 있고, 구조를 유지한 채 스타일만 바꾸는 수준을 넘어 완전히 다른 시각적 지문으로 재설계할 수도 있다.

특히 `study`는 참고 사이트를 그대로 복제하는 기능이 아니다. 마음에 드는 디자인에서 매크로 구조, 폰트 조합, 색상 축과 같은 원리를 뽑아내고, 그것을 새로운 프로젝트에 적용할 수 있는 형태로 정리하는 흐름이다. 좋은 레퍼런스를 복사하는 대신, 왜 좋아 보이는지를 학습하는 방식에 가깝다.

## 구조를 먼저 고르고, 테마는 그다음에 입힌다

Hallmark의 흥미로운 점은 색상부터 고르지 않는다는 것이다. 먼저 페이지의 매크로 구조를 결정한다. 콘텐츠가 어떤 순서로 흐르고, 사용자가 어디에서 멈추며, 어떤 요소가 시각적 중심이 될지를 정한 뒤 테마와 디테일을 붙인다.

이 순서는 중요하다. 같은 색상 팔레트를 사용하더라도 다음 구조는 완전히 다른 인상을 만든다.

- 제품의 핵심 메시지를 크게 밀어붙이는 편집형 구조
- 정보의 양과 비교를 우선하는 도구형 구조
- 이미지와 분위기로 기억을 만드는 브랜드형 구조
- 지표와 조작 요소를 빠르게 찾게 하는 운영형 구조

AI에게 “세련된 SaaS 랜딩 페이지”라고만 요청하면 기존에 많이 보았던 SaaS 패턴이 나올 가능성이 높다. Hallmark는 이 모호한 요청을 제품의 성격에 맞는 구조적 선택으로 먼저 분해하려고 한다.

좋은 디자인은 색상 토큰을 바꾸는 것만으로 만들어지지 않는다. 무엇을 먼저 보여주고, 어디에 여백을 두고, 어떤 요소를 반복하고, 사용자가 다음에 무엇을 하게 만들지 결정하는 데서 시작한다.

## 21개 테마가 의미하는 것

Hallmark에는 여러 개의 시각적 테마가 포함되어 있다. 중요한 것은 테마의 개수가 아니라, 같은 요구사항에 언제나 같은 모양을 적용하지 않도록 하는 장치라는 점이다.

예를 들어 기술 인프라 제품에는 정교하고 단단한 구조가 어울릴 수 있지만, 차 브랜드나 음반 레이블에는 같은 밀도와 대비를 적용하기 어렵다. Hallmark는 브리프의 분위기와 제품의 성격에 따라 서로 다른 시각 언어를 선택하려 한다.

테마는 단순한 색상 조합이 아니다.

- 제목과 본문 사이의 타이포그래피 대비
- 화면의 밀도와 여백의 비율
- 섹션이 연결되는 방식
- 테두리, 그림자, 질감의 사용 정도
- 버튼과 인터랙션이 내는 목소리

이런 요소들이 함께 하나의 테마를 만든다. 그래서 결과물이 서로 다른 프로젝트에서 단순히 색상만 바꾼 템플릿처럼 보이지 않는 것을 목표로 한다.

## 57개의 안티패턴 검사와 자기 비평

Hallmark는 생성된 결과물을 바로 넘겨주지 않고 여러 개의 디자인 검사와 사전 자기 비평을 거친다고 설명한다. 이 검사의 목적은 코드가 컴파일되는지 확인하는 것이 아니다. 화면이 흔한 AI 기본값에 너무 가까운지를 점검하는 것이다.

이 접근은 테스트의 의미를 넓힌다. 보통 프론트엔드 테스트는 다음을 확인한다.

- 버튼이 클릭되는가?
- API 응답이 올바르게 표시되는가?
- 작은 화면에서 레이아웃이 깨지지 않는가?

이것들은 반드시 필요하다. 하지만 제품의 인상을 결정하는 질문은 별도로 존재한다.

- 첫 화면에서 무엇이 가장 중요한지 알 수 있는가?
- 모든 섹션이 같은 카드와 같은 간격으로 반복되지 않는가?
- 폰트와 색상이 제품의 성격을 설명하는가?
- 장식이 목적 없이 붙어 있지 않은가?
- 다른 생성 결과와 구별할 수 있는 시각적 결정이 있는가?

Hallmark의 안티패턴 검사는 후자의 질문을 자동화된 체크리스트로 다루려는 시도다. 자동 검사가 디자인을 대신할 수는 없지만, 반복되는 실수를 일찍 발견하는 안전망은 될 수 있다.

## Custom 모드는 템플릿을 벗어나는 출구다

카탈로그 안의 테마로 프로젝트의 의도를 충분히 표현하기 어려운 경우 Hallmark는 `Custom` 분기를 사용한다. 이때는 미리 정해진 테마를 고르는 대신 색상, 폰트, 레이아웃을 프로젝트에 맞춰 새로 구성한다.

이 기능은 모든 결과를 무작위로 만들자는 뜻이 아니다. 오히려 일반적인 브리프에는 검증된 선택지를 사용하고, 창의적인 방향이 강한 프로젝트에서만 템플릿 밖으로 나가도록 경로를 분리한다.

디자인 시스템도 비슷한 균형이 필요하다. 모든 화면을 매번 새로 만들면 일관성이 무너지고, 모든 화면을 같은 컴포넌트로만 만들면 제품의 개성이 사라진다. 반복 가능한 기반과 예외를 허용하는 창의적 공간을 함께 설계해야 한다.

## AINSOFT의 개발 흐름에서 어디에 쓸 수 있을까

AINSOFT처럼 운영 자동화와 지식검색 제품을 다루는 팀에서는 기능의 정확성만큼 제품의 성격을 전달하는 화면도 중요하다. Hallmark의 개념을 적용하면 다음과 같은 흐름을 만들 수 있다.

### 새 화면을 만들 때

먼저 사용자의 작업 맥락과 화면의 역할을 정리한다. 운영 대시보드인지, 제품 소개 페이지인지, 지식검색 결과인지에 따라 정보 밀도와 우선순위가 달라진다. 그다음 화면의 매크로 구조를 결정하고, 제품의 브랜드에 맞는 시각 언어를 선택한다.

### 기존 화면을 개선할 때

기능을 건드리기 전에 화면의 반복 패턴을 점검한다. 카드가 너무 많지는 않은지, 모든 제목이 같은 크기인지, 사용자가 다음 행동을 찾기 어려운지 확인한다. 이 단계에서는 `audit`처럼 문제 목록을 먼저 만드는 방식이 유용하다.

### 전면 재설계가 필요할 때

기존 카피와 정보 구조가 이미 검증됐다면 모든 내용을 다시 쓰지 않고 시각적 구조만 바꿀 수 있다. 반대로 화면이 제품의 핵심 사용 방식을 가리고 있다면 `redesign`처럼 구조 자체를 다시 선택해야 한다.

### 좋은 레퍼런스를 발견했을 때

참고 사이트의 색상을 복사하기보다 구조와 리듬을 분석한다. 어떤 요소가 시선을 끄는지, 콘텐츠가 어떤 순서로 등장하는지, 글자와 이미지가 어떤 긴장을 만드는지를 기록하면 팀의 디자인 언어로 전환하기 쉬워진다.

## Hallmark가 해결하지 않는 것

Hallmark가 유용해 보여도 이것만 설치하면 좋은 제품 화면이 자동으로 완성되는 것은 아니다. 몇 가지 책임은 여전히 팀에 남는다.

- 실제 사용자의 문제를 발견하고 우선순위를 정하는 일
- 브랜드의 역사와 고객 맥락을 이해하는 일
- 접근성, 성능, 국제화, 유지보수성을 검증하는 일
- 화면의 문구가 제품의 실제 기능과 일치하는지 확인하는 일
- 생성된 코드가 보안과 데이터 처리 규칙을 지키는지 검토하는 일

또한 “AI스럽지 않음”과 “좋은 디자인”은 같은 말이 아니다. 일부러 낯선 색상과 복잡한 레이아웃을 선택한다고 해서 제품의 사용성이 좋아지는 것은 아니다. 차별화는 목적이 아니라 결과여야 한다. 사용자가 더 빨리 이해하고, 더 확신을 갖고, 더 적은 실수로 행동할 수 있을 때 시각적 개성이 의미를 갖는다.

## 설치와 시작점

Hallmark는 다음 명령으로 설치할 수 있다.

```bash
npx skills add nutlope/hallmark
```

Claude Code, Cursor, Codex에 맞는 설치 위치가 안내되어 있으며, 규칙 파일과 참고 자료를 프로젝트 범위 또는 개인 범위에 둘 수 있다. MIT 라이선스라서 저장소를 살펴보고 팀의 개발 흐름에 맞게 활용하기도 좋다.

다만 설치보다 먼저 팀의 기준을 정하는 편이 좋다. 우리 제품에서 절대 놓치면 안 되는 정보는 무엇인지, 어떤 시각적 기본값을 피하고 싶은지, 접근성과 성능을 어떤 수준으로 검증할지를 정의해야 한다. Hallmark는 그런 기준을 대신 만들어주는 제품이라기보다, 에이전트가 디자인을 더 진지하게 다루도록 만드는 출발점이다.

## 마무리

Hallmark의 가장 흥미로운 점은 AI에게 더 창의적으로 만들라고 막연히 요구하지 않는다는 데 있다. 대신 구조를 고르고, 테마를 선택하고, 흔한 안티패턴을 검사하고, 결과를 비평하는 절차를 작업 흐름에 넣는다.

생성형 개발의 다음 경쟁력은 코드를 얼마나 빨리 만들어내는가에만 있지 않다. 같은 속도로 만들어진 결과 중에서 어떤 제품이 더 분명한 의도와 기억할 만한 인상을 남기는가에도 있다.

좋은 에이전트는 개발자의 손을 빠르게 만들 뿐 아니라, 선택의 질을 높여야 한다. Hallmark는 그 선택의 질을 디자인 영역에서 끌어올리려는 작지만 분명한 시도다. AINSOFT의 제품 화면을 만들 때도 이 원칙은 유효하다. 기능을 구현한 뒤 장식을 더하는 것이 아니라, 제품의 목적과 사용자의 맥락에서 시작해 구조와 시각 언어를 함께 결정하는 것. AI 시대의 프론트엔드 작업에서 그 차이가 점점 더 커질 것이다.
