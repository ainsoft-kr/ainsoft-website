# AINSOFT Website — Experience Spine

→ 구성 시안: [`.working/home-direction-v2.html`](.working/home-direction-v2.html). 이 문서와 시안이 다르면 이 문서를 따릅니다.

## Foundation

반응형 웹 단일 화면군입니다(Flutter Web, `responsive_framework`). 모바일, 태블릿, 데스크톱을 모두 지원합니다. 시각 기준은 `DESIGN.md`를 따릅니다.

**오디언스 계층화 원칙:** 홈과 각 페이지의 첫 화면은 운영팀장·CTO(구매 결정권자)를 위한 것이고, 페이지 안쪽과 하위 페이지로 들어갈수록 개발자를 위한 정보가 됩니다. 기술 용어의 밀도는 깊이에 비례해서 높아집니다.

**핵심 메시지:** 방문자가 홈을 떠날 때 "AINSOFT는 운영 자동화 제품(AISOpsFlow · Ainsoft RAG)과 현장 맞춤 AI 구축 서비스를 제공하는 회사"라고 기억해야 합니다. 두 축은 같은 비중으로 다룹니다.

## Information Architecture

기존 7개 메뉴를 로고(홈) + 메뉴 5개 + 상담 버튼으로 재구성합니다. 기존 경로는 모두 유지하고 이름만 바꿉니다.

| 메뉴 (새 이름) | 기존 | 경로 | 주 대상 | 목적 |
|---|---|---|---|---|
| 로고 → 홈 | Home | `/` | 운영팀장·CTO | 무엇을 제공하는 회사인지 기억시키기 |
| 제품 | Products | products | CTO → 개발자 | 두 제품의 역할, 묶음과 개별 도입, 아래로 갈수록 아키텍처 |
| AI 구축 서비스 | Services | services | CTO → 개발자 | 구축 가능한 AI 유형과 진행 방식 |
| 활용 사례 | Solutions | solutions | 운영팀장 | 조직 유형별 도입 전후 장면 |
| 회사 소개 | About | about | 전체 | 신뢰와 채용 |
| 블로그 | Post | posts | 개발자 | 기술 글 |
| 도입 상담 (버튼) | Contact | contact | 전체 | 전환 |

### 홈 구성 (순서 고정)

| # | 섹션 | 답하는 질문 | 깊이 |
|---|---|---|---|
| 1 | 히어로 | 우리 문제와 관련 있나? | 최소: 분류 한 줄, 헤드라인, 한 문장, 상담 버튼, 흐름 링크 |
| 2 | AINSOFT가 제공하는 두 가지 | 무엇을 파는 회사인가? | 같은 비중의 카드 두 장 |
| 3 | 동작 흐름 (감지 → 근거 찾기 → 승인 → 실행 → 보고) | 실제로 어떻게 일을 줄이나? | **가장 자세하게.** 단계별 담당 제품 표시, 아래에 개발자용 아키텍처 링크 |
| 4 | 적용 장면 3개 | 우리 같은 팀에도 맞나? | 장면마다 전/후 각 한 줄. 제품 1, 구축 서비스 1, 둘 다 1 |
| 5 | 도입 부담 줄이기 | 보안과 연동은 괜찮나? | 세 항목, 각 한 문장 |
| 6 | 마지막 상담 유도 | 다음에 뭘 하면 되나? | 버튼 하나 |

홈에서 빠지는 것: 상단 키워드 띠, 히어로 오른쪽 정보 카드와 질문형 지표 카드 3개, Positioning·Products·Solutions 카드 섹션(2·3번 섹션으로 통합), 섹션별 "○○ 보기" 버튼.

### 상세 페이지 공통 구성

| 순서 | 블록 | 대상 |
|---|---|---|
| 1 | 페이지 히어로: 분류, 2줄 제목, 한 문단, 도입 상담 버튼, "개발자 정보 바로 보기" 링크 | 결정권자 |
| 2 | 같은 비중의 카드 2~3장 (무엇을 하는지) | 결정권자 |
| 3 | 짧은 목록 (도입 방식 / 확장 영역 / 담당자별 변화) | 결정권자 · 실무자 |
| 4 | 어두운 "개발자를 위한 정보" 영역: 항목별 기술 사양 + GitHub 저장소 링크 | 개발자 |
| 5 | 마지막 상담 유도 | 전체 |

- **GitHub 링크는 유지합니다.** 오픈소스는 사용자가 직접 확인해야 하므로, 본문 속 주소 텍스트가 아니라 새 탭으로 열리는 저장소 링크로 개발자 영역에 모읍니다.
- 회사 소개 페이지는 개발자 영역 없이 일하는 방식 3가지와 대표 소개로 구성합니다.
- 활용 사례 페이지는 개발자 영역 없이 조직별 전/후 장면 6개(제품 4, 구축 서비스 2)와 담당자별 변화 3개로 구성합니다.
- 상담 페이지는 실제 연락 수단이 핵심입니다: "메일로 상담 신청"(제목과 적을 항목이 채워진 메일 열기), 이메일 · 전화 링크, "확인 후 1일 안에 회신" 안내, 적어 주면 좋은 3가지, 상담 주제 4가지.
- 제거한 것: 숫자처럼 보이지만 숫자가 아닌 지표 카드 전부, 같은 설명을 반복하던 Value · Fit · Combined · Approach 섹션.

## Voice and Tone

| Do | Don't |
|---|---|
| "운영팀이 반복하던 일을 AI 워크플로우로 바꿉니다." | "운영 자동화와 지식검색을 하나의 흐름으로 연결합니다." (무엇이 좋아지는지 없음) |
| 고객의 업무로 말하기: "승인 한 번으로 실행" | 제품 구조로 말하기: "Core ↔ Runner 하이브리드 배포" (홈에서) |
| 한국어 메뉴와 제목 | Positioning, Combined Value 같은 영문 라벨 |
| 문장 하나에 메시지 하나 | 두세 문장으로 같은 내용 반복 |
| 근거가 없으면 장면으로 보여주기 | 근거 없는 수치나 "최고의" 같은 표현 |

## Component Patterns

| Component | Use | Behavioral rules |
|---|---|---|
| 상단 메뉴 | 전 페이지 | 데스크톱(1024px 이상)은 메뉴 5개와 오른쪽 끝 "도입 상담" 버튼입니다. 그보다 좁으면 로고, 작은 "도입 상담" 버튼, 메뉴 버튼(홈, 메뉴 5개, 도입 상담)을 한 줄에 둡니다. 현재 페이지를 표시합니다. |
| 주 버튼 | 전 페이지 | 페이지에서 강조색 버튼은 "도입 상담" 하나뿐입니다. 다른 이동은 `link-arrow`로 처리합니다. |
| 제공 카드 | 홈 2번 섹션 | 카드 전체가 아니라 아래 링크만 누를 수 있습니다. 제품 카드는 제품 페이지로, 구축 카드는 AI 구축 서비스 페이지로 이동합니다. |
| 흐름 그림 | 홈 3번, 제품 페이지 | 정적 그림입니다(애니메이션 없음). 담당 태그로 묶음 구성을 설명하므로 별도의 "Together" 카드를 두지 않습니다. |
| 적용 장면 | 홈 4번, 활용 사례 페이지 | 홈에는 3개만 둡니다. 전체 목록은 활용 사례 페이지에 둡니다. |
| 상세 정보 (개발자용) | 제품·구축 서비스 페이지 하단 | 아키텍처, SDK, 저장소 링크는 페이지 아래쪽 "개발자를 위한 정보" 영역에 모읍니다. 본문 안에 URL을 그대로 쓰지 않고 링크 버튼으로 만듭니다. |

## State Patterns

| State | Surface | Treatment |
|---|---|---|
| 페이지 이동 | 전체 | 이동 시 스크롤을 맨 위로 되돌립니다(현재 구현 유지). |
| 상담 신청 | contact | 신청서 서버가 없으므로 메일 앱으로 신청합니다. 버튼 바로 아래에 "확인 후 1일 안에 회신드립니다."를 항상 보여줍니다. |
| 수치/고객사 확보 시 | 홈 4번 | 장면 하나를 실제 사례로 교체합니다. 수치가 생기기 전에는 숫자 카드를 쓰지 않습니다. |

## Interaction Primitives

- 모든 이동은 일반 링크입니다. 호버 효과는 밑줄과 색 변화 정도로만 둡니다.
- "어떻게 동작하나요 →"는 같은 페이지의 흐름 섹션으로 부드럽게 스크롤합니다.

## Accessibility Floor

- 메뉴와 버튼은 키보드로 이동할 수 있고 포커스가 보여야 합니다.
- 흐름 그림은 순서 있는 목록 구조로 만들어 화면 낭독기가 단계 순서를 읽을 수 있어야 합니다.
- 버튼과 링크의 글자는 행동을 드러내야 합니다("보기" 대신 "제품 자세히 보기").
- 화면 낭독기를 고려해 Flutter `Semantics`로 제목 위계를 표시합니다.

## Responsive & Platform

| 너비 | 변화 |
|---|---|
| 1024px 이상 | 메뉴 노출, 제공 카드 2열, 흐름 5단 가로, 장면 3열 |
| 600~1023px | 메뉴는 메뉴 버튼으로, 제공 카드 2열, 흐름과 장면은 세로 목록 |
| 600px 미만 | 모든 그리드 1열. 헤드라인은 단어 중간에서 끊기지 않도록 줄바꿈을 직접 지정합니다(Flutter는 한글 단어 단위 줄바꿈을 지원하지 않음) |
| 모바일 (600px 미만) | 상담 버튼은 헤더에 항상 노출합니다. 하단 탭 바는 홈, 제품, 구축 서비스, 활용 사례, 블로그이고, 상담은 헤더와 중복되므로 넣지 않습니다. 회사 소개는 헤더 메뉴에서 접근합니다. |

## Key Flows

### 김 팀장, 반복 업무에 지친 IT 운영팀장
1. 지난주 새벽 장애 대응 회의 뒤에 "운영 자동화"를 검색하다가 홈에 들어옵니다.
2. 헤드라인 "운영팀이 반복하던 일을 AI 워크플로우로 바꿉니다"를 보고 계속 읽기로 합니다.
3. 두 번째 섹션에서 이 회사가 제품과 구축 서비스를 제공한다는 것을 파악합니다.
4. **흐름 그림에서 사람에게 남는 일이 "승인" 하나뿐인 것을 보고 "이거다"라고 느낍니다.** (결정적 순간)
5. 적용 장면 중 "새벽 장애 알림"이 자기 상황이라는 것을 확인합니다.
6. 헤더의 "도입 상담"을 누릅니다.

### 박 CTO, 보안이 걱정인 제조사 기술 책임자
1. 김 팀장에게서 링크를 받고 홈에 들어옵니다.
2. 제공 카드에서 "현장 맞춤 AI 구축" 카드를 보고 공장 검사 이미지 문제를 떠올립니다.
3. **"도입 부담 줄이기"에서 데이터가 사내에 머문다는 점을 확인합니다.** (결정적 순간)
4. "구축 서비스 보기"로 들어가 진행 방식을 확인하고, 개발자에게 아래쪽 기술 정보를 전달합니다.
5. 도입 상담을 신청합니다.

## Open Items

- 웹사이트 안에서 바로 보내는 상담 신청서가 필요하면 별도 서버(또는 폼 서비스)가 있어야 합니다.
- 제품·구축 서비스·활용 사례 상세 페이지도 같은 원칙(첫 화면은 결정권자, 아래는 개발자)으로 정리할지는 다음 단계에서 정합니다.
